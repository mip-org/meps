## Summary

Today a package reaches mip users only through a channel: a separate `mip-<channel>` repository whose CI builds `.mhl` files from a recipe and serves an index from GitHub Pages. Here we propose a second route in which a package's own GitHub repository builds and publishes its `.mhl` files. The repository keeps `mip.yaml` at its root and adds one short workflow file that calls a reusable workflow in `mip_channel_tools`. That workflow runs the same per-architecture build and test pipeline a channel uses, attaches the resulting `.mhl` files to the repository's GitHub releases, and maintains an `index.json` in the channel index format as a release asset.

On the client side, users install by pointing at the repository:

```matlab
mip install fastalgorithms/chunkie
mip install https://github.com/fastalgorithms/chunkie@1.2.0
```

Such packages stay under the existing `gh` source type, with the 3-part FQN `gh/<owner>/<repo>`, installed next to the channel packages of the same owner. In this sense the repository is both a channel and a package. The 2-part form `<owner>/<repo>`, which today means a package in the owner's personal channel, now means the repository; if the repository publishes no mip package, mip falls back to the personal channel and says so. Because the repository's index has the same schema as a channel index, version selection, architecture selection, dependency resolution, and `mip update` reuse the existing channel code; only the location of the index differs.

## Motivation

A limitation of the current distribution model is that every published package needs a channel, and a channel is a second repository with its own conventions (`packages/<name>/<version>/source.yaml`, the `mip-` naming rule, GitHub Pages setup). For an organization distributing many packages this is a reasonable cost. For an author with one MATLAB package, it is a substantial amount of machinery to stand up and maintain alongside the repository they actually work in. The channel also separates the act of releasing (tagging the package repository) from the act of publishing (adding a release directory to the channel), so the two can drift.

The alternatives available to such an author today each lose something:

- **Submit to `mip-org/core`.** This works well for widely used packages, but it puts a review step between the author and their users, and is not appropriate for every package.
- **Host a personal channel.** `mip-example` shows that a channel with a single package is possible. The author still maintains two repositories and a recipe that points from one to the other.
- **Install from a source zip.** `mip install https://github.com/o/r/archive/main.zip` already works and lands under `web/<name>`. However, nothing is compiled in CI (so MEX packages require a compiler on the user's machine), the package is never tested in a clean environment, and `mip update` cannot refresh it because the source URL is not retained.
- **Attach a hand-built `.mhl` to a release.** `mip install <url>.mhl` installs it as `mhl/<name>`, but the author must build each architecture by hand, and the result cannot be updated.

The authors' view is that the natural unit for many packages is the repository itself: the author tags a release, CI produces tested binaries for each architecture, and users install by naming the repository. This is the model familiar from other ecosystems where a repository's releases carry its build artifacts.

We emphasize that this proposal does not replace channels. Channels remain the right tool for curated collections, for packaging third-party code the packager does not control, and for overlaying channel-side `mip.yaml` or compile scripts. A repository that publishes its own releases can still be included in a channel through an ordinary `source.yaml`.

## Proposal

This section is organized as follows. First we describe what the package author adds to their repository. Next we describe what the publishing workflow produces and where. We then describe the client-side source type, install syntax, and resolution rules. Finally we list the concrete changes to `mip_channel_tools` and to mip.

### 1. What the author adds

The repository has `mip.yaml` at its root, exactly as for a local install or an upstream-sourced channel recipe. The author adds one file, `.github/workflows/mip.yml`:

```yaml
name: mip
on:
  push:
    tags: ['v*']
    branches: [main]      # optional: publish a rolling "main" build
  workflow_dispatch:
permissions:
  contents: write
jobs:
  mip:
    uses: mip-org/mip_channel_tools/.github/workflows/repo-build.yml@main
```

Like the channel caller workflows, this file owns only its triggers and delegates all logic to `mip_channel_tools`. It references `repo-build.yml@main`, as channel callers do; we do not pin to a versioned tag of `mip_channel_tools`. The repository must be public, for two reasons: MATLAB on GitHub-hosted runners is licensed only for public repositories, and users download release assets anonymously.

The package name in `mip.yaml` must equal the repository name, up to the usual name equivalence ([spec §1.8](https://github.com/mip-org/mip/blob/main/docs/specification.md#18-name-equivalence)) and case. This keeps the last component of the FQN equal to the package name (§5). A repository whose name is not a valid mip name (for example one containing a dot) cannot publish this way.

**Scaffolding.** `mip init -g` ("Prepare to host on GitHub as a single-package repository") writes `.github/workflows/mip.yml`. It can be run together with `mip init`, after it, or again later to update the workflow. Plain `mip init` does not write the workflow, since a package may not be hosted on GitHub (or kept in git at all), or may be built by a channel that includes it rather than by its own repository. In that last case a workflow in the package repository would publish a second, unintended set of releases.

### 2. Versions

The version of a build is determined by the ref that triggered it:

- A pushed tag `v1.2.0` or `1.2.0` builds version `1.2.0`. A leading `v` is stripped only when the remainder is numeric in the sense of `mip.resolve.is_numeric_version`. If `mip.yaml` declares a numeric `version`, it must equal the tag's version, and the workflow fails before building anything if it does not. Authors may also leave `version` blank and let the tag decide.
- A push to a branch listed in the caller's `branches:` builds a non-numeric version named after the branch (e.g. `main`), which follows the same rules as a `main` release directory in a channel ([spec §11.2.1](https://github.com/mip-org/mip/blob/main/docs/specification.md#1121-channel-version-rules)).
- A tag whose name is not numeric after stripping `v` (e.g. `v1.2.0-beta`) is published under its literal name. Since `select_best_version` prefers numeric versions, such a build is installed only when requested explicitly with `@`.

This reuses the channel's existing notion of a version, so `.release_version`, `mip.json`'s `version`, and the client's version selection need no new rules.

### 3. What is published, and where

- **Versioned builds** attach their `.mhl` and `.mhl.mip.json` assets to the GitHub release for the triggering tag, creating the release if only the tag exists. Authors thus see their build artifacts on the release they already make, rather than on a parallel release.
- **Branch builds** attach their assets to a single fixed release with tag `mip-index`, marked as a prerelease so it never becomes the repository's "Latest" release. Each new branch build replaces the previous assets of the same name.
- **The index** is an asset named `index.json` on the `mip-index` release. Its schema is the channel index schema (`packages`, `github_repo`, `last_updated`, optional `mip_compatibility_floor`), and its entries are the `.mhl.mip.json` sidecars with `mhl_url` and `mip_json_url` added. All entries share one package name.

The client fetches the index from

```
https://github.com/<owner>/<repo>/releases/download/mip-index/index.json
```

We chose a release asset over GitHub Pages because many package repositories already use Pages for documentation, and because Pages requires a manual settings change before the first build. We chose it over the GitHub REST API because unauthenticated API requests are limited to 60 per hour per IP address, which is easily exceeded on shared networks; release asset downloads are not subject to that limit.

The index is regenerated from the sidecars of all releases on every run, rather than edited incrementally. A release deleted by the author therefore drops out of the index on the next run, and `workflow_dispatch` can be used to regenerate the index without building. Note that replacing `index.json` is not atomic: `gh release upload --clobber` deletes and re-uploads the asset, so a client fetching during that interval sees a 404 and fails with `mip:indexFetchFailed`. This is the same class of problem as the non-atomic channel publish described in [mip-org/mip#201](https://github.com/mip-org/mip/issues/201), and a retry succeeds.

### 4. The publishing workflow

`repo-build.yml` in `mip_channel_tools` has three jobs:

1. **plan** checks out the repository, determines the version (§2), reads `builds[].architectures` from `mip.yaml`, and intersects them with the architectures CI can build (`any`, `linux_x86_64`, `macos_arm64`, `windows_x86_64`, `numbl_wasm`). Its output is the build matrix.
2. **build** calls the existing `build-package.yml` once per architecture, with new inputs `mode: repo`, `version`, and `release_tag`. Reusing that workflow, rather than copying it, keeps the runner choices, toolchain setup, glibc gate, toolchain stripping before tests, and MEX coverage check identical to channel builds.
3. **index** runs once after the whole matrix, under a concurrency group, so the per-architecture jobs do not race to rewrite `index.json`.

In repo mode, `build-package.yml` differs from a channel build as follows:

- The package repository is checked out into a subdirectory (e.g. `pkgsrc/`) at the triggering commit. Checking it out at the workspace root, as channel builds do, would place `mip/`, `mip_channel_tools/`, and `build/` inside the package tree, where they would be hashed and copied.
- `prepare` takes the source directory and the version explicitly instead of deriving them from `packages/<name>/<version>/`, excludes `.git` from the copy and the source hash, and records the triggering commit as `.commit_hash`.
- The skip-if-unchanged check looks for an existing sidecar on the target release tag. For a branch build this skips a rebuild when the commit has not changed; for a tag build it makes re-runs idempotent.
- The test step installs the built `.mhl` without `--channel`, so bare-name dependencies resolve against `mip-org/core` only, as they will for users (§7). The channel test derives a channel name by stripping `mip-` from the repository name, which would be wrong here.
- The per-build `assemble-and-deploy` job (GitHub Pages) is skipped; the `index` job of `repo-build.yml` replaces it.

The Windows vcpkg binary cache uses the `MIP_CACHE_TOKEN` secret when present and otherwise builds native dependencies from source with a warning, so it requires no change. `macos_x86_64` cannot be built on GitHub-hosted runners for the same reasons as in channels; supporting it would require extending `mip-channel local-build` to repo mode, which we leave to future work.

### 5. FQN and installed location

A repository package uses the existing `gh` source type with a 3-part FQN:

| Canonical FQN | Installed at |
|---|---|
| `gh/<owner>/<repo>` | `<root>/packages/gh/<owner>/<repo>/` |

It sits next to the channels of the same owner, whose packages are installed at `<root>/packages/gh/<owner>/<channel>/<name>/`. Loosely speaking, the repository is a channel that holds exactly one package, so the package directory is the repository directory itself. Since the package name equals the repository name (§1), the last component of the FQN is still the package name, and bare-name resolution among installed packages, which matches on directory names, needs no change.

We considered a separate source type, `repo/<owner>/<repo>/<name>` (see Alternatives). It would need fewer changes to the path helpers, which today assume that every `gh` FQN has four parts. We prefer `gh` because a repository package is a GitHub package in the same sense that a channel package is, and because its display form (below) is the same string the user types to install it.

**Telling channels and repositories apart on disk.** Under `<root>/packages/gh/<owner>/`, a directory that contains `mip.json` is a repository package; any other directory is a channel whose subdirectories are packages. `list_installed_packages` and the other path helpers branch on this. Note that a channel `foo` lives in the repository `mip-foo` but is installed under `gh/<owner>/foo/`, so an owner with both a channel `foo` and a package repository `foo` would map both to the same directory. An install that would create this overlap fails with `mip:repo:conflictsWithChannel`, and a channel install that would overlap an installed repository package fails in the same way. We expect this to be rare.

**Display form.** The display form strips `gh/` as before, so `gh/fastalgorithms/chunkie` displays as `fastalgorithms/chunkie`. The personal-channel collapse (`gh/<owner>/<owner>/<pkg>` displayed as `<owner>/<pkg>`) would now produce a string that reads as a repository package, so we propose to drop it: personal-channel packages display as `<owner>/<owner>/<pkg>`.

**Case.** GitHub treats owner and repository names case-insensitively, while mip compares owner and channel strictly. To avoid installing the same repository twice under different spellings, the client canonicalizes `<owner>/<repo>` to the `github_repo` field the index already carries.

### 6. Install syntax

`mip install` accepts the following forms for a repository package, each with an optional `@version` suffix:

| Argument | Meaning |
|---|---|
| `<owner>/<repo>` | Repository install, with fallback to the personal channel (below) |
| `gh/<owner>/<repo>` | Repository install (explicit FQN, no fallback) |
| `https://github.com/<owner>/<repo>` | Repository install (no fallback) |
| `github.com/<owner>/<repo>` | Same, without the scheme |

**The 2-part form.** Today `<owner>/<name>` is shorthand for `gh/<owner>/<owner>/<name>`, the package `<name>` in the owner's personal channel (repository `mip-<owner>`). Under this proposal it first means the repository `github.com/<owner>/<name>`. If that repository publishes no mip package, that is, if the download of its `index.json` (§3) returns 404, mip prints a message and falls back to the personal channel:

```
github.com/magland/chunkie does not publish a mip package.
Installing chunkie from the personal channel magland/magland instead.
```

Only a 404 triggers the fallback. Other failures, such as a network error or an invalid index, are raised rather than masked by the fallback. If neither the repository nor the personal channel provides the package, the error names both locations. We chose this order because, once single-package repositories are available, we expect few authors to maintain a personal channel. The explicit 3-part form `<owner>/<owner>/<name>` always reaches the channel without probing the repository.

Commands that act on installed packages (`load`, `unload`, `uninstall`, `update`, `info`) resolve a 2-part `<owner>/<name>` against what is installed: `gh/<owner>/<name>` if present, otherwise `gh/<owner>/<owner>/<name>`.

**URL forms.** A trailing `/` or `.git` is accepted. Other paths under `github.com` (e.g. `/archive/...zip`, `/releases/download/...mhl`) keep their existing meaning. Categorization happens before the existing rule that sends every other `https://` URL to the `.mhl` path; today a bare repository URL takes that path and fails with an unhelpful "not a ZIP" error. The scheme-less form currently fails to parse because dots are not allowed in package names, so it is free to take.

The package name comes from the index. If the index publishes no package, more than one distinct name, or a name that differs from the repository name, the install raises `mip:repo:invalidIndex`. Once installed, the package can be referred to by bare name (`mip load chunkie`) under the usual bare-name rules, or as `fastalgorithms/chunkie`.

`--channel` does not apply to repository arguments, in the same way it does not apply to FQN arguments.

### 7. Resolution, dependencies, and update

Internally, a channel becomes one kind of **index source**: either a channel `{<owner>, <channel>}`, whose index is on GitHub Pages, or a repository `{<owner>, <repo>}`, whose index is the release asset of §3. Index fetching, caching, and `build_package_info_map` take an index source instead of an owner/channel pair, and produce 4-part or 3-part `gh/` FQNs accordingly. Repository indexes are cached under `<root>/cache/repo-index/<owner>/<repo>.json` with the same TTL; they cannot share `<root>/cache/index/<owner>/`, where `<repo>.json` could be the cache of a channel of the same name. A repository install then follows the same request, plan, and execute steps as a channel install.

Dependencies follow the existing rules with two additions:

- A bare-name dependency of a repository package resolves to `mip-org/core` only, not to the installing user's subscribed channels. The author cannot know which channels a user subscribes to, so a dependency outside core must be named explicitly. This is also the rule a non-core `gh` parent already falls back to when its own channel does not provide the dependency; a repository's index provides only itself.
- An explicit dependency in `mip.yaml` may be written as `github.com/<owner>/<repo>` (with or without `https://`), as `gh/<owner>/<repo>`, or as a channel FQN, so one repository package can depend on another. The 2-part `<owner>/<repo>` is not accepted in a dependency list, since its fallback would make the dependency resolve differently depending on which repositories exist when the user installs. `build_graph` lazily fetches repository indexes as it does channel indexes.

`mip update` treats repository packages as remote packages: it re-fetches the repository's index and applies the existing version and timestamp comparison. An installed branch build (e.g. `main`) continues to follow that branch, as it does for channels. No new provenance field is stored, since the FQN encodes the repository. `mip info` shows remote information for repository packages, and `mip avail <owner>/<repo>` lists the versions and architectures in the repository's index.

[MEP 9](mep-0009.md)'s lock file can record repository packages exactly as it records channel packages, since each index entry has an `mhl_url` and digest. Tag builds have stable asset URLs; branch builds are rolling, as `main` builds in channels are.

### 8. Summary of changes

In `mip_channel_tools`:

- New reusable workflow `repo-build.yml` (§4), whose plan job also checks that the package name equals the repository name (§1).
- `build-package.yml`: `mode`, `version`, and `release_tag` inputs; subdirectory checkout; skip `assemble-and-deploy` in repo mode. Separately, `test-and-upload` should honor `source_repo` as the build job does.
- `prepare`: `--source-dir`, `--version`, and `--release-tag`; no `source.yaml` requirement in repo mode; exclude `.git`; skip check against the given tag.
- `assemble-index`: a repo mode that collects sidecars from all releases by package name, rather than filtering by `packages/<name>/<release>/source.yaml`, and uploads `index.json` to the `mip-index` release.
- `test_one.m` and the `numbl_wasm` test step: install without `--channel` in repo mode.
- `upload` already accepts `--release-tag` and needs no change.

In mip:

- `parse_package_arg`: the 3-part `gh/<owner>/<repo>` form, the URL forms, and the 2-part form as a repository reference with personal-channel fallback (§6). `display_fqn`: 3-part `gh` FQNs, and no personal-channel collapse (§5).
- Path and state helpers that assume 4-part `gh` FQNs: `get_package_dir`, `installed_dir`, `installed_fqn`, `cleanup_package_parents`, and `list_installed_packages`, which must tell repository packages from channel directories (§5).
- `install.m` argument categorization and the fallback (§6).
- `index_url`, `fetch_index`, `build_package_info_map`, `from_repository`, and `build_graph` take an index source (§7).
- `update.m` treats repository packages as remote; `info.m` and `avail.m` support them.
- `mip init -g` (§1).
- Specification §1.1, §1.5, §2.1, §3.0, §3.1, §7, §11; tests with an offline index helper analogous to `writeChannelIndex`.

Documentation gains an article on publishing from one's own repository, with pointers from "Creating a package" and "Hosting a channel".

## Backward compatibility

Two existing argument forms change meaning:

- **The 2-part form `<owner>/<name>`** now refers first to the repository `github.com/<owner>/<name>`. Existing uses that mean a personal-channel package keep working through the fallback of §6, with a printed message, unless the owner also has a repository named `<name>` that publishes a mip package. In that case the explicit `<owner>/<owner>/<name>` is needed. Installed personal-channel packages are unaffected on disk, but display as `<owner>/<owner>/<name>` (§5).
- **A 3-part argument starting with `gh/`** (e.g. `gh/a/b`) is today implicit `gh/gh/a/b`, the channel `a` of a GitHub owner named `gh`; it now means the repository `github.com/a/b`. Such a channel remains reachable through the explicit 4-part form `gh/gh/a/b`. This mirrors how the existing reserved prefixes (`fex`, `web`, ...) already shadow 2-part personal-channel shorthand for owners with those names.

Arguments of the form `https://github.com/<owner>/<repo>` currently fail with an error, so giving them a meaning breaks nothing. Existing installed channel directories contain no `mip.json` at the channel level, so the on-disk rule of §5 classifies them correctly. Existing channels and their indexes are unaffected.

The publishing workflow requires no change to existing channels; `build-package.yml` defaults to channel mode.

## Alternatives

**Serve the index from GitHub Pages, as channels do.** This would make a repository look exactly like a channel to the client. It fails for repositories that already use Pages for documentation, requires a manual settings change, and the client would still need to know that the index is not at `<owner>.github.io/mip-<repo>`, since the `mip-` naming rule does not apply. We prefer the release asset.

**Discover releases through the GitHub REST API.** No index would need to be maintained. However, unauthenticated requests are limited to 60 per hour per IP address, which a classroom or institute network can exhaust quickly, and the client would have to download every sidecar to learn dependencies and architectures. We prefer a precomputed index.

**Keep the index on a branch** (e.g. `mip-index`, fetched from `raw.githubusercontent.com`). A branch push is atomic, which avoids the brief 404 window of §3. On the other hand, it adds a branch to the author's repository and is subject to a few minutes of CDN caching. This is a reasonable alternative; we prefer keeping all mip output under Releases, but the choice is not essential to the design.

**Publish to mip-owned tags** (`<name>-<version>`, as channels do) rather than the author's tags. This requires fewer tooling changes, since `upload` and the skip check already derive tags this way. The cost is a second release next to every release the author makes (`chunkie-1.2.0` beside `v1.2.0`), which we expect authors to find confusing.

**A separate source type, `repo/<owner>/<repo>/<name>`.** This was the first draft of this proposal. It keeps the 4-part shape of channel FQNs, so the path helpers need fewer branches, and it lets the package name differ from the repository name. On the other hand, it adds a reserved prefix, its display form differs from the install argument, and a repository package is no less a GitHub package than a channel package is. A two-part `repo/<name>`, like `fex/<name>`, would be simpler still, but two repositories publishing the same package name would collide in it.

**Keep `<owner>/<name>` for personal channels** and require the URL form for repositories. This changes no existing meaning. However, it gives the short form to what we expect to be the less common case, and it leaves repository installs with a longer syntax than channel installs.

**Recommend single-package channels instead.** This needs no client change. It keeps the cost this proposal aims to remove: a second repository, the `mip-` naming rule, Pages setup, and a recipe that can drift from the package's own releases.

## Open questions

- **Package name versus repository name.** We require them to be equal (§1). The alternative is to let them differ and have bare-name resolution read the name from `mip.json` for repository packages. This would support a repository such as `chunkie-matlab` publishing `chunkie`, at the cost of a second matching rule.
- **Personal-channel display.** Dropping the collapse (§5) keeps display forms unambiguous, but makes `mip list` output longer for users of personal channels.
- **Hosts other than GitHub.** For now we assume repository packages are hosted on GitHub, which matches where the build workflow runs and simplifies the design. Supporting other hosts later would need its own source type; the `https://<host>/<owner>/<repo>` install form extends to them naturally.
